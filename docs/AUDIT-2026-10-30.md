# KOE Syndicate project audit — 30 October 2026

Started 30 October; final local API verification completed 31 October 2026 (Asia/Calcutta).

Assessment: a substantial hackathon prototype with a buildable frontend, but not ready for an unrestricted public, multi-user production launch. Authentication boundaries, durable workflow execution, and truthful demo/live behavior need attention before additional agents or integrations.

## Scope and current status

- Local HEAD and GitHub main both resolve to `860a7f607127f4075f8631d60ee395c7ebc0b7ef`.
- GitHub public API: 0 open issues, 0 open pull requests, 0 workflow runs, 0 releases. No tracked `.github` workflows were found. These counts do not establish code quality or reveal private security alerts / branch protection.
- Existing untracked pitch documents and presentation were left untouched.
- Reviewed backend routes, OAuth/session storage, service entry points, agent execution, phone/email/calendar tools, BigQuery integration, frontend state flows, requirements, deployment files, and tests.
- No deployed service was penetration-tested. No actual call, email, Calendar event, or cloud database mutation was initiated by the audit.
- The audit does not establish that the deployed application uses this exact commit or configuration.

## Highest-priority findings

### 1. Critical if publicly reachable: business APIs and callbacks lack authentication

Evidence: `ui_client/main.py:1255`, `:1281`, `:1429`, `:1476`, `:1494`, `:1554`, `:1570`, and the human-input routes. `FastAPI` has no application-wide auth dependency; these routes do not validate a user or service identity. `deploy_cloud_run.sh:48` explicitly allows unauthenticated service access.

An unauthenticated client can inject a business through `/agent_callback`, read pipeline data, request SDR execution with a phone override, reset the shared pipeline, or submit human-input responses. Actual call charges depend on configured and functioning downstream providers. CORS and the frontend Calendar login screen do not authorize API requests.

Local in-process reproduction confirmed: anonymous callback 200, business read 200, outreach 200 with mocked SDR invoked once, and reset 303. No real outbound provider call occurred. This verifies the application authorization gap; actual internet exposure still depends on deployment ingress controls.

Fix: require authenticated users for browser routes, signed service identity for agent callbacks/A2A, tenant ownership checks, request limits, and per-user spending quotas. Keep internal agents private. Add negative tests proving anonymous and cross-tenant requests cannot mutate state or trigger provider tools.

### 2. High: every user shares pipeline state and WebSocket broadcasts

Evidence: `ui_client/main.py:167`, `:182`, `:1255`, `:1445`; agent services use in-memory stores and shared A2A user identifiers.

All dashboard connections receive the same businesses and updates; a new search resets everyone's pipeline. Restarts lose state and separate workers/replicas maintain conflicting copies. WebSocket connections have neither user authentication nor Origin validation.

Fix: persist tenant-owned campaigns, leads, jobs, and events; scope sockets by authenticated tenant/campaign; use a shared event broker and durable job queue. Reject stale callbacks from older or cancelled runs.

### 3. High: OAuth state is not a security nonce

Evidence: `ui_client/main.py:372–399`. State is empty or base64-encoded city/niche, and the callback never compares it with a browser-bound, one-time nonce. This creates login-CSRF/account-confusion risk.

Fix: use cryptographically random state bound to the initiating browser, short expiry and one-time consumption; store navigation data server-side; use a supported OAuth flow with PKCE. URL-encode return query parameters. Also require a non-default session secret at startup (`:179`), remove unconditional insecure OAuth transport (`:23`), and disable debug mode (`:246`). A known signing key alone does not reveal the random database session IDs, but it removes a security boundary.

### 4. High: Calendar credentials are selected by recency instead of job ownership

Evidence: `ui_client/main.py:561–592`; `ui_client/db.py:146–158`; `lead_manager/lead_manager/tools/calendar_utils.py:20–24`.

The internal credentials route falls back to the most recently connected Google user. A workflow without tenant identity can therefore act on the wrong Calendar. The caller hardcodes `http://localhost:8000`, which addresses its own container when services are separately deployed; the UI endpoint also rejects remote callers by IP. Merely replacing localhost with a service URL will not solve authorization.

Fix: carry verified tenant/user identity end-to-end and perform scoped Calendar operations behind authenticated service calls, preferably without exporting raw tokens. Eliminate the latest-user fallback. Store refresh tokens encrypted in durable storage. `/auth/disconnect` currently deletes a session, not the stored Google credentials, despite its docstring.

### 5. Critical dependency finding: Next.js 16.2.10 and vulnerable transitive packages

Evidence: `frontend/package.json`, lockfile, saved live npm audit. npm identifies `next` as critical and proposes 16.4.3 as the available fix at audit time. Other affected packages include sharp, postcss, source-map-js, zod, nanoid, js-yaml, browserslist, brace-expansion, and baseline-browser-mapping.

The [Next.js Windows RCE advisory](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36) covers the installed version. Other advisories have feature/configuration preconditions. No exploit was attempted and the Linux deployment manifests do not establish Windows-server exposure.

Fix: upgrade Next.js and matching lint configuration, refresh transitive dependencies, inspect remaining advisories by reachable feature, then run build, lint, smoke tests and a fresh audit. Do not blindly apply a forced major-version audit fix.

### 6. High: Python requirements pin known vulnerable versions

Evidence: `ui_client/requirements.txt:4–6`; installed metadata confirms `python-multipart==0.0.6`, `jinja2==3.1.2`, `python-jose==3.3.0`, and requests 2.31.0.

`python-multipart` 0.0.6 is affected by [CVE-2024-24762](https://github.com/advisories/GHSA-2jv5-9r88-3w3p), relevant to public form-handling routes. Jinja's [upstream changelog](https://jinja.palletsprojects.com/en/stable/changes/) documents security fixes after 3.1.2. Python-jose's [3.4.0 release](https://github.com/mpdavis/python-jose/releases/tag/3.4.0) addresses older security issues; newer advisories must also be considered before choosing a target version. No application import of jose was identified in the reviewed code, so removal may be preferable.

Fix: run a full Python dependency audit for each deployment environment, remove unused packages, upgrade supported versions, and create reproducible locks. This review checked selected advisories, not every installed Python package.

### 7. High, conditional tool exposure: BigQuery filters interpolate strings into SQL

Evidence: `lead_finder/lead_finder/tools/bigquery_utils.py:611–644`. City, category and lead_status are embedded in SQL quotes; limit and rating are directly interpolated too. Quotes in normal business inputs can break the query, and malicious tool arguments can alter it. External reachability depends on which agent invokes this tool and its IAM permissions.

Fix: use BigQuery typed query parameters, bounded numeric values, and least-privilege IAM. Add fixtures containing apostrophes and SQL metacharacters. `check_hot_lead` already demonstrates parameter binding elsewhere in this repository.

## Workflow defects

### 8. High: demo mode performs real Calendar writes

Evidence: `frontend/src/app/dashboard/page.tsx:222`, `:307`; `ui_client/main.py:502–536`.

Both demo runners call the real schedule endpoint when authenticated. Automatic fallback after a lead-finder failure can therefore book a synthetic lead. Repeated runs create duplicate events, and the UI sets `meeting_scheduled` even when Calendar creation failed.

Fix: enforce demo/live mode server-side, make demo tools incapable of external writes, explicitly confirm live booking, use idempotency keys, and derive success status from the provider result.

### 9. High: Gmail listener fails before listening and can lose notifications

Evidence: `gmail_pubsub_listener/gmail_listener_service.py:245–270` uses `pull(..., callback=..., flow_control=...)`. Installed SDK inspection confirms those arguments are unsupported. [Google's reference example](https://docs.cloud.google.com/pubsub/docs/pull-messages) uses `subscribe` for callback streaming.

The exception is swallowed inside `start_listening`, so the caller's cron fallback does not activate for this failure. The notification handler also starts history retrieval at the received history ID instead of a persisted previous cursor (`:111`), ignores pagination, and can acknowledge notifications even when downstream processing fails. The trigger URL at `:204` is not declared by the reviewed Lead Manager servers; HTTP error statuses are logged as successful triggers rather than rejected.

Fix: use the correct subscriber API; propagate startup failure; persist mailbox history cursors and processed message IDs; page through history; use the actual A2A contract; acknowledge only after durable acceptance; retry with deduplication and a dead-letter queue.

### 10. High operational risk: phone polling blocks the async service without a deadline

Evidence: `sdr/sdr/tools/phone_call.py:74`, `:147–148`, `:354`. Async functions use synchronous SDK operations and `time.sleep`; polling is unbounded until a recognized terminal status arrives.

Fix: use nonblocking waits and a thread for blocking SDK calls, total deadlines, cancellation, bounded retry and durable call-status tracking. Missing configuration currently produces a synthetic positive transcript rather than a clear live-mode error; mark simulation explicitly and prevent downstream live actions.

### 11. Medium: Calendar availability includes the past

Evidence: `lead_manager/lead_manager/tools/calendar_utils.py:41` generates whole business days without clipping them to the requested start/end datetimes. A local extracted-function test with start `2026-10-30T15:30:00+00:00` returned 09:00 and seven already-past slots.

Fix: intersect business hours with the requested interval, handle timezone/DST transitions correctly, use paginated events or FreeBusy, and recheck conflicts before booking. The demo booking endpoint also hardcodes Asia/Kolkata and a fixed time without availability checks.

### 12. Medium: reported BigQuery meeting persistence does not happen

Evidence: `lead_manager/lead_manager/tools/bigquery_utils.py`, `save_meeting_arrangement`. BigQuery initialization/table selection are commented out; the function writes JSON and logs BigQuery success.

Fix: implement and verify the insert, or return an explicit local-only/degraded status. Use durable storage for fallbacks and distinguish accepted, persisted and failed writes.

### 13. Medium: frontend realtime recovery and human approvals are incomplete

Evidence: `frontend/src/app/dashboard/page.tsx:104–158`, `:381–391`.

- No WebSocket reconnect/backoff or snapshot recovery after a disconnect.
- `render.yaml` configures the HTTP backend URL but not `NEXT_PUBLIC_WS_URL`; the frontend defaults to `ws://localhost:8000/ws` in production unless configured separately.
- Reset clears local React state without resetting/cancelling backend work; demo timers are not cancelled and repopulate state after reset.
- The new frontend does not handle `human_input_request` events or expose the legacy approval-response flow.
- After an anonymous demo finishes, `isDemoRunning=false` returns the user to the connect-Calendar screen, hiding results.
- Any failed outreach response is presented as exhausted billing/credits, masking validation, authentication, service or network errors.

Fix: centralize an explicit campaign state machine, cancel tracked timers/jobs, derive WebSocket URLs from the backend URL, reconnect with event cursors, implement approval UI, retain completed demo results, and preserve real error categories.

### 14. Medium: container and deployment manifests omit required pieces

Evidence: `Dockerfile.ui_client` copies only common and ui_client; it omits `lead_scoring_ml.py` and `demo_leads.json`. Startup catches the missing scoring import, leaving scores unavailable. `render.yaml` omits the Gmail listener, UI-to-Lead-Manager URL, frontend origin configuration, WebSocket URL, and much of OAuth configuration. Separate dashboard settings may compensate, but the manifest alone is incomplete.

SQLite tokens and in-memory workflows have no declared durable deployment storage. `.gcloudignore` excludes `.env` but not `.secrets`, `tokens.db`, `.git`, or frontend dependencies; sensitive/local files can enter upload context. Selective Docker COPY reduces final-image exposure but does not prevent build-context upload.

Fix: document and validate a single deployment topology, include intended assets, use durable managed storage, restrict build contexts, and run container-level health and contract checks.

### 15. Medium: scoring claims exceed the implemented data flow

Evidence: `lead_scoring_ml.py:43–60` uses 15 mock training examples; `frontend/src/components/dashboard/data.ts:104–112` assigns fixed scores. The dashboard does not fetch `/api/lead-scores`; the backend Business model also omits score/rating/industry fields. Rescoring substitutes rating 4.0 and industry General. The CPU engine label can say sklearn even when only the rating fallback ran.

Fix: label scores as demonstration data until validated; carry real feature values and lead IDs; integrate scores into the API/UI; report the actual execution engine. Use real labeled outcomes with holdout evaluation and calibration before presenting percentages as conversion probabilities.

## Additional risks and improvements

- Plaintext refresh tokens and client secrets in `tokens.db`, full transcript/proposal logging, and JSON backups need encryption, retention limits, access controls and redaction. No evidence of an actual credential breach was established.
- Prompt injection is a design risk where external website/email content reaches agents that can send mail or create meetings. Add tool-level recipient/tenant/operation policy and action approval; prompt wording alone is insufficient. An adversarial end-to-end test was not performed.
- `lead_manager/simple_main.py:18–54` accepts a caller-supplied `ui_client_url` and posts to it: an SSRF risk if this fallback service is exposed. Replace it with trusted configuration or a strict destination allowlist.
- `/api/system-status` makes a Maps request for each caller and calls phone readiness true based on partial credentials, without verifying the phone-number ID/provider state. Cache health results and distinguish configured, reachable, authorized and funded.
- UI backend debug mode and public debug/test routes reveal operational details or allow synthetic actions. Disable them in production.
- Several landing-page navigation, policy and footer links are placeholders. Product claims, pricing and agent-count claims should match working features; README's enumerated agent categories sum to 32 while it advertises 34.
- International leads are offered but `validate_us_phone_number` accepts US-style numbers. Add explicit supported markets and validated E.164 normalization.

## Recommended additions, in order

1. **Trustworthy execution:** tenant authentication/roles, agent identity, durable campaign/job state, idempotent external actions, audit trail, cancellation and spending caps.
2. **Safe outreach controls:** suppression/opt-out list, campaign approval queue, contact-source/provenance fields, timezone-aware contact windows, and a clear live/demo indicator enforced by tools.
3. **Reliability:** retries and dead-letter handling, provider readiness dashboard, correlated traces, failure alerts, backup/restore verification and deployment smoke tests.
4. **Useful sales workflow:** deduplicate by place ID/domain/normalized phone, editable lead profiles, search/filter/export, real call/email timelines, meeting confirmation/reschedule/cancel, and CRM synchronization after core stability.
5. **Measured intelligence:** grounded pitch citations, agent evaluations with adversarial fixtures, actual funnel metrics/cost per outcome, and calibrated lead scoring from real historical outcomes.
6. **Repository hygiene:** GitHub Actions for lint/build/unit/contract tests, Python and npm audits, secret scanning, dependency update automation, CONTRIBUTING/SECURITY documentation, and tagged releases.

Recommended sequence: close auth/data-access and dependency issues first; fix Gmail, Calendar, async execution and demo boundaries second; introduce persistence and CI third; expand product capabilities afterward.

## Verification limits

Backend test details: `venv/Scripts/python.exe -m pytest ui_client/test/test_ui_client.py -q --tb=short` completed outside the sandbox after sandboxed Windows asyncio socket creation hung. The failures are old landing-page text expectations, two redirects followed by TestClient (200 versus expected 303), empty-form validation (422 versus expected 400), and a missing-name callback (400 versus expected 200). These indicate test/contract drift, not five independent production defects. The installed pytest-asyncio does not recognize `asyncio_default_fixture_loop_scope`. Update test contracts, use `follow_redirects=False` when asserting redirects, and separate provider integration scripts from offline unit tests. The entire repository test suite was not run because some scripts directly contact external providers.

This is a source/dependency audit with selected local reproductions, not a security certification. Cloud IAM, actual production ingress, provider billing, DNS/TLS, deployed logs, Google OAuth app settings, private GitHub security alerts, full-history secrets and real end-to-end outreach were not verified. No source fixes or dependency upgrades were applied.
